# Multus CNI deployment on whoverse (Phase 2a: infrastructure only)

- **Date:** 2026-08-07
- **Status:** Approved design (pending spec review)
- **Owner:** home-ops maintainers

## 1. Problem

We want LAN-native (non-tailnet) networking for KubeVirt VMs as part of the
Phase 2 work deferred in the [KubeVirt deployment design]
(2026-08-05-kubevirt-deployment-design.md): VMs get a second NIC on VLAN 3
(`172.16.3.0/24`, LAN-native) via a Multus `bridge` NAD (`master: br0`,
`vlan: 3`).

This spec covers **only the Multus infrastructure deployment** (CNI plugin +
DaemonSet + Cilium integration). The NAD itself, IPAM strategy, and KubeVirt
bridge binding are a **separate phase** (see §8), per explicit user scoping.

## 2. Verified environment facts

Cluster facts verified against the live cluster / repo (2026-08-07):

## 3. Design decisions (agreed with user)

1. **Deployment vehicle: vendored official thick DaemonSet**, not a Helm chart.
   The upstream project ships no chart. The `angelnu/helm-charts` `multus`
   chart (v7.0.0, wraps v4.3.0, built on bjw-s `common` 5.0.1) was evaluated
   and rejected: third-party chart, plus a redundant `cni-installer` init
   container (Talos already bundles those plugins). Vendoring matches the
   existing kubevirt-operator precedent and the Talos docs' prescribed path.
2. **No system extension / no node reboot.** Multus binaries land in
   `/opt/cni/bin` (Talos-writable) via the DaemonSet's `install-multus-binary`
   init container. Only the `multus` binary is installed; reference plugins
   come from Talos itself.
3. **Cilium integration = one flag: `cni.exclusive: false`.**
   - Default `exclusive: true` makes Cilium's install-cni rename non-Cilium
     configs (`00-multus.conf`) to `*.cilium_bak` on agent restarts — which
     kills Multus cluster-wide. This is the Talos-doc-referenced requirement.
   - **No `chainingMode` change.** Current Cilium charts only offer
     `none|aws-cni|flannel|generic-veth|portmap` (the `multus` chaining mode
     is gone). The model is Multus-as-meta-plugin: kubelet → `00-multus.conf`
     → delegates to Cilium's untouched `05-cilium.conf` for pods without NAD
     annotations.
4. **Phasing: Multus now, NAD later.** This phase installs Multus + the
   `NetworkAttachmentDefinition` CRD but creates **no NADs**. The VLAN-3
   bridge NAD, IPAM (mix of DHCP + static per-VM — both are used on
   `172.16.3.0/24`), and KubeVirt bridge binding land in the next phase.

## 4. Architecture

```
kubelet ──► 00-multus.conf  (multus meta-plugin, auto-generated by daemon)
              ├── default delegate ──► 05-cilium.conf   (existing Cilium, unchanged)
              └── per-NAD annotation ──► future bridge/vlan-3 NAD (next phase)
```

- `kube-multus-ds` DaemonSet in `kube-system`:
  - hostNetwork, hostPID, `priorityClassName: system-node-critical`,
    privileged, tolerates all taints
  - init container `install-multus-binary` → copies `multus` binary to
    `/host/opt/cni/bin` (thick mode)
  - container `kube-multus` runs `multus-daemon`; ConfigMap
    `multus-daemon-config` sets `"multusConfigFile": "auto"` — daemon reads
    the first non-multus CNI config (`05-cilium.conf`, the only one present
    since Talos `cniConfig: none`) and generates `00-multus.conf`
  - ships the `network-attachment-definitions.k8s.cni.cncf.io` CRD (idle
    until the NAD phase)
- Existing pods are unaffected at rollout: their netns persists; only *new*
  pods flow through the multus → cilium chain.

## 5. Repo changes

```
kubernetes/kube-system/
├── kustomization.yaml                     # + multus/ks.yaml
└── multus/
    ├── ks.yaml                            # dependsOn: cilium; healthCheck: kube-multus-ds
    └── app/
        ├── kustomization.yaml
        ├── multus-daemonset-thick-v4.3.0.yaml   # vendored from v4.3.0 release tag
        └── patches/
            └── talos.yaml                 # strategic-merge patches
```

### 5.1 Cilium HelmRelease change

`kubernetes/kube-system/cilium/app/helmrelease.yaml`:

```yaml
values:
  cni:
    exclusive: false
```

### 5.2 Talos patch (strategic-merge, `patches/talos.yaml`)

1. **`host-run-netns` volume**: `hostPath.path: /run/netns/` →
   `/var/run/netns/`. Mandatory on Talos — the hostPath must point at the
   real netns dir (container-side `mountPath: /run/netns` stays as-is).
   Skipping this cripples new pod creation cluster-wide.
2. **Image pin**: `ghcr.io/k8snetworkplumbingwg/multus-cni:snapshot-thick`
   → `stable-thick-amd64` (verify at implementation; prefer a versioned tag
   or digest if one becomes available — see §9 risks). Two occurrences
   (init container + main container).

### 5.3 Ordering

`multus/ks.yaml` carries `spec.dependsOn: [{name: cilium}]` so the daemon
only auto-generates its config once Cilium's `05-cilium.conf` exists.

Both changes land in one commit; runtime sequence is:

1. Cilium agents rollout with `exclusive: false` (safe — no other CNI configs
   exist yet).
2. `kube-multus-ds` rolls out; daemon writes `00-multus.conf`.
3. New pods flow kubelet → multus → cilium. Existing pods untouched.

## 6. Validation

- `just flate-test` before/after changes; pre-commit (gitleaks/trufflehog)
  before commit — vendored manifest is clean upstream, scan anyway.
- Post-deploy checks:
  1. `kubectl -n kube-system get ds kube-multus-ds` — all 5 nodes Ready.
  2. On a node: `/etc/cni/net.d/00-multus.conf` exists and `05-cilium.conf`
     intact; `/opt/cni/bin/multus*` present.
  3. `kubectl get network-attachment-definitions` — CRD registered (empty).
  4. Pod-churn test: `kubectl rollout restart` a benign deployment → new pods
     schedule and become Ready (proves the kubelet→multus→cilium default
     path without any NAD).
  5. `cilium status --wait` healthy; no new CiliumNetworkPolicy breakage.
- Rollback: revert the commit + `flux reconcile source git home-ops` /
  `flux reconcile kustomization cluster`. Manual cleanup after DS removal:
  delete `00-multus.conf` from `/etc/cni/net.d` and
  `/opt/cni/bin/multus*` on each node (the vendored DS has no uninstall hook;
  the rejected angelnu chart had one).

## 7. Out of scope (next phase)

- VLAN-3 bridge NAD: `master: br0`, `vlan: 3`, `172.16.3.0/24`. IPAM will
  mix **DHCP and static per-VM** (both patterns exist on that VLAN).
- KubeVirt bridge binding (`interfaces[].bridge` + `networks[].multus`).
- ARM64 Multus image support (cluster is amd64).

## 8. Risks / verification points

- **Cluster-wide new-pod dependency on multus→cilium chain** — once
  `00-multus.conf` exists, all new pod creation goes through it. Mitigated by
  `dependsOn: cilium`, staged rollout, and the rollback procedure (§6).
- **Image tag situation** — no `v4.3.0-thick` semantic tag in the registry;
  `stable-thick-amd64` is floating. Verify at implementation; if only
  `snapshot-thick*` resolves, weigh digest-pinning (Renovate tracks digests)
  vs. floating `stable-thick`. The repo's `fix/latest-tag-pinning` worktree
  signals this matters — pick the most pin-able option available.
- **Generated config filename** — expected `00-multus.conf`; confirm the
  daemon's output name at implementation (rollout test is the gate).
- **Cilium agent restart window** — brief per-node CNI reconfig during the
  `exclusive: false` rollout; standard for Cilium config changes.
- **v4.3.0 release note** — DeviceID ordering is now deterministic
  (alphabetical). Irrelevant today (no device-plugin NADs), noted for the NAD
  phase.
