# kro prep implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up the kro controller in the home-ops cluster with no `ResourceGraphDefinition` definitions yet — just the namespace, OCI HelmRepository, and a pinned HelmRelease with RBAC aggregation mode and metrics scraping enabled.

**Architecture:** Mirror the existing `node-feature-discovery` / `external-secrets` pattern for a system controller: one `kro-system` namespace (Flux-owned), one OCI `HelmRepository/kro` pointing at `oci://registry.k8s.io/kro/charts`, one `HelmRelease/kro` pinned to v0.9.2 with `rbac.mode: aggregation`, `metrics.service.create: true`, `metrics.serviceMonitor.enabled: true`. Existing two-line edits to two top-level `kustomization.yaml` files.

**Tech Stack:** Flux CD v2 (Kustomization + HelmRelease v2 + HelmRepository + OCIRepository), kro v0.9.2 (kubectl-style controller, OCI Helm chart), kustomize, kubeconform, pre-commit.

- [ ] **Step 1: Create `kubernetes/kro-system/kustomization.yaml`**

Write to `kubernetes/kro-system/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

  - kro/ks.yaml
```

Notes:
- Ordering: `ns.yaml` first, per the structure rule "namespace kustomization must reference `ns.yaml` first".
- File name is `ns.yaml` (matching AGENTS.md), not `namespace.yaml` (which kopiur-system uses — that one is an existing inconsistency and not the new convention).

- [ ] **Step 2: Create `kubernetes/kro-system/kro/ks.yaml`**

Write to `kubernetes/kro-system/kro/ks.yaml`:

```yaml
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: kro
  namespace: kro-system
spec:
  interval: 30m
  path: "./kro-system/kro/app"
  sourceRef:
    kind: OCIRepository
    name: home-ops
    namespace: flux-system
  healthChecks:
    - apiVersion: apps/v1
      kind: Deployment
      name: kro
      namespace: kro-system
  timeout: 10m
  wait: true
  prune: false
```

Notes:
- Mirrors `kubernetes/kube-system/node-feature-discovery/ks.yaml` exactly except for the namespace + name.
- `metadata.namespace: kro-system` matches the parent directory, satisfying the structure rule "component ks.yaml metadata.namespace must match parent namespace directory".
- No `dependsOn` — kro has no upstream system prerequisite.

- [ ] **Step 4: Create `kubernetes/kro-system/kro/app/helmrelease.yaml`**

Write to `kubernetes/kro-system/kro/app/helmrelease.yaml`:

```yaml
---
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: kro
  namespace: kro-system
spec:
  interval: 30m
  chart:
    spec:
      chart: kro
      version: 0.9.2
      sourceRef:
        kind: HelmRepository
        name: kro
        namespace: flux-system
      interval: 24h
  install:
    createNamespace: false
    remediation:
      retries: 3
    strategy:
      name: RetryOnFailure
      retryInterval: 5m
  upgrade:
    remediation:
      retries: 3
    strategy:
      name: RetryOnFailure
      retryInterval: 5m
  values:
    rbac:
      mode: aggregation
    config:
      enableLeaderElection: true
      logLevel: info
    metrics:
      service:
        create: true
        type: ClusterIP
        port: 8078
      serviceMonitor:
        enabled: true
```

Notes:
- `version: 0.9.2` is the latest kro release as of 2026-07-25 (verified via `curl -sL https://api.github.com/repos/kubernetes-sigs/kro/releases/latest | jq -r '.tag_name'` → `v0.9.2`). Renovate will bump it.
- `rbac.mode: aggregation` is kro's documented recommended setting (chart's default is `unrestricted`).
- `metrics.service.create: true` + `metrics.serviceMonitor.enabled: true` exposes `:8078/metrics` and creates a `ServiceMonitor` that the in-cluster VictoriaMetrics picks up automatically.
- `createNamespace: false` matches every other `HelmRelease` in this repo that uses a Flux-owned namespace.
